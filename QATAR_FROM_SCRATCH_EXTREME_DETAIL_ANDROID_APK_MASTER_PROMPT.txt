H. Honest evidence

3. TRUE 1:1 SCALE, GLOBAL COORDINATES, AND FLOATING ORIGIN
----------------------------------------------------------

Use true 1:1 local metre scale.

- One projected metre equals one game metre.
- Human, car, boat, helicopter, aeroplane, roads, runways, ports, buildings, and terrain use physically meaningful dimensions.
- Do not compress the peninsula into a small theme park.
- Do not enlarge airport runways or use hidden aircraft takeoff impulses.

Coordinate system:

- Store master positions in double precision.
- Default to WGS84 / UTM zone 39N (EPSG:32639), which covers Qatar, after verifying it against source metadata and known checkpoints. If an authoritative source uses Qatar National Grid or another CRS, perform a documented verified conversion into the single runtime master CRS rather than guessing offsets.
- Verify EPSG definition, axis order, units, false easting/northing, datum, and transform with known checkpoints.
- Keep latitude/longitude only for metadata and conversion; do not feed degrees to physics/render calculations.
- Use local float coordinates around the active focus for GLES/Bullet.
- Implement a floating origin for the full-country distances.
- Keep global double transform plus local float transform for every streamed/static/dynamic entity.

Origin rebase:

- Trigger beyond a profiled local-distance threshold, not every frame.
- Shift terrain chunks, rigid bodies, constraints, vehicles, human, camera, particles, audio, water-wave origin, traffic, pedestrians, transit, AI paths, decals, tire tracks, and sky/environment anchors coherently.
- Preserve linear/angular velocity, forces, gear state, wheel state, rotor/propeller phase, route progress, and render interpolation.
- Rebuild/update Bullet broadphase safely after a shift.
- Ensure asynchronous chunk requests use immutable global keys and cannot apply stale pre-shift local coordinates.

Required coordinate tests:

- WGS84 to projected to WGS84 round-trip at north, south, east, west, and Doha checkpoints.
- Projected distance/orientation against known open-data road/runway lengths/headings.
- Save/load at opposite country extremes.
- Human walking during rebase.
- Car at highway speed during rebase.
- Boat during waves/current during rebase.
- Helicopter and aeroplane during rebase.
- Traffic/transit paths during rebase.
- No visible jump greater than a small documented render tolerance.
- No change in local velocity/acceleration beyond numeric tolerance.

6. DETERMINISTIC GIS AND WORLD-COMPILATION PIPELINE
---------------------------------------------------

Pipeline stages:

STAGE 1 — Acquire and verify
- Fetch from recorded URLs.
- Verify transport success, byte size, format magic, checksum, expected date, and geographic intersection.
- Never commit an HTML error page as data.

STAGE 2 — Normalize coordinates
- Parse WGS84 safely.
- Project into selected metre CRS.
- Normalize axis order.
- Reject NaN/infinity/out-of-range coordinates.
- Preserve source IDs/tags needed for reproducibility.

STAGE 3 — Validate geometry
- Repair only safely repairable polygons.
- Reject self-intersections that cannot be deterministically resolved.
- Normalize winding.
- Remove duplicate/near-duplicate points.
- Snap shared road/intersection endpoints within a documented tolerance.
- Preserve bridge/tunnel/layer separation.
- Validate coastline rings/holes/islands.

STAGE 4 — Clip and classify
- Clip land/detail to national AOI.
- Retain a configurable water/airspace buffer.
- Classify municipalities, settlements, land use, terrain class, road class, water class, protected/restricted/generalized zones, and material region.
- Keep source confidence/provenance on inferred values.

STAGE 5 — Terrain synthesis
- Resample DEM without inventing mountains.
- Qatar is low/flat; preserve subtle relief and avoid exaggerated fantasy terrain.
- Generate microrelief only through documented biome-specific rules.
- Constrain roads, runways, building pads, ports, and shore structures.
- Generate dune/sabkha/rock detail layers separately from base elevation.

STAGE 6 — Networks
- Build routable right-hand road/lane graph.
- Build sidewalk/crossing graph.
- Build metro/tram rail splines and station metadata.
- Build marine navigability/depth/current zones.
- Build aircraft runway/taxiway data.

STAGE 7 — Structures
- Compile all valid building footprints/levels/heights/roof types/tags.
- Build deterministic procedural style parameters.
- Preserve important landmark/skyline identifiers.
- Generate collision proxies and LOD hierarchy.

STAGE 8 — Chunking
- Create hierarchical country/region/chunk IDs.
- Dense Doha/Lusail chunks may be 128–256 m.
- Other towns may be 256–512 m.
- sparse desert/coast may use 512 m–2 km data tiles with subcells for collision/detail.
- Create coarse whole-country terrain/road/city massing independent of near chunks.

STAGE 9 — Runtime compilation
- Versioned binary magic/header.
- CRS/origin/epoch version.
- Bounds/count limits.
- Material/asset dependency table.
- Geometry quantization only within measured error limits.
- LODs/collision/nav metadata.
- Compression suitable for random chunk access.
- Per-chunk checksum.
- Master manifest checksum.

STAGE 10 — Validation report
- Country/municipality feature counts.
- Missing/invalid geometry counts.
- Chunk coverage map.
- Seam report.
- Road/rail connectivity report.
- Coast/island report.
- Height/material inference statistics.
- Runtime byte totals.
- Determinism hash.

The build must never silently substitute an old compiled world when source/compiler version changed.


7. STREAMING ARCHITECTURE FOR THE ENTIRE COUNTRY
------------------------------------------------

The complete country cannot be loaded in full detail. Streaming is foundational.

Chunk lifecycle:

- UNLOADED.
- REQUESTED.
- QUEUED_IO.
- DECODING_CPU.
- READY_CPU.
- QUEUED_GPU.
- ACTIVE_HIGH.
- ACTIVE_MEDIUM.
- ACTIVE_LOW.
- EVICT_PENDING.
- EVICTED.
- FAILED_OPTIONAL or FAILED_REQUIRED.

Required behavior:

- Select chunks using global focus, camera, altitude, velocity, heading, vehicle mode, braking/turn radius, graphics profile, and thermal profile.
- Walking/car/boat/heli/aeroplane have different predictive load corridors.
- Aeroplane high-altitude view uses coarse country terrain/settlement/road massing plus high detail only near camera/flight corridor.
- Keep collision terrain farther ahead than visible high-detail props for fast vehicles.
- Decode on bounded worker threads.
- GL uploads only on GL thread under per-frame time/byte budget.
- Prioritize safety collision, terrain, roads, and runway before decoration.
- Cancel stale requests after rapid turns/teleports.
- Reference-count shared materials/meshes/textures.
- Evict with hysteresis to prevent boundary thrash.
- Never evict occupied-vehicle collision support.
- Keep water analytic globally and load coast/harbor detail by chunk.
- Use deterministic fallback coarse terrain if an optional decoration bundle fails; required terrain/collision failure must show a safe error, not an invisible hole.

Suggested rings:

ON FOOT
- High detail/collision: 250–500 m.
- Medium structures/vegetation: 0.5–1.5 km.
- Low city/desert massing: several km.

CAR/4X4
- High road/collision: 500–1,000 m biased forward.
- Medium: 1–3 km.
- Coarse horizon and route graph: farther.

BOAT
- High shore/obstacle/depth: based on speed, typically 500–1,500 m.
- Medium coast/port/islands: multiple km.
- Analytic sea/horizon: global.

HELICOPTER
- Collision/building high corridor scaled by speed/altitude.
- Medium city/terrain multiple km.
- Coarse country/skyline to horizon.

AEROPLANE
- Coarse whole-country terrain always available.
- Runway/airport high detail for departure/approach.
- Predictive terrain/building corridor many seconds ahead.
- Altitude-aware suppression of street props.

Memory rules:

- No entire-country building mesh in RAM.
- No entire-country road render mesh in RAM.
- Global route graph uses compact topology/attributes.
- Coarse whole-country representation has a strict budget.
- Texture pages are shared and evicted by material region/LOD.
- Avoid duplicate vertex arrays after GPU upload where CPU copies are not needed.
- Keep collision data only in safety rings and route-specific caches.
- Record CPU heap, native heap, Bullet memory, texture bytes, vertex/index bytes, audio, and pending decode bytes separately.

Streaming tests:

- Abu Samra to Doha to Al Ruwais drive.
- Doha to Dukhan drive.
- Doha to Al Khor/Ras Laffan region.
- Doha to Mesaieed/Khor Al Adaid approach.
- Coastline boat trip through multiple water/coast classes.
- Helicopter cross-country route.
- Aeroplane full peninsula circuit.
- Repeated north-south traversal with stable memory.
- Pause/resume during decode/upload.
- Teleport between every municipal test hub.
- Reverse direction at high speed.
- Corrupt optional decoration chunk fallback.
- Missing required terrain chunk hard failure before publication.


8. QATAR TERRAIN AND ENVIRONMENT BIOME SYSTEM
---------------------------------------------

Do not depict Qatar as one uniform yellow dune texture. Implement distinct physically plausible environmental classes from legal mapped data and deterministic procedural masks.

A. Rocky limestone/gravel desert (hamada)

- Common flat/rolling stony surface.
- Pale limestone/gravel albedo variation.
- Sparse stones, low microrelief, compacted vehicle tracks.
- Roughness/normal detail at multiple scales.
- Sparse hardy shrubs only where land-cover/confidence supports them.
- Do not add dense vegetation.

B. Sand sheets and dunes

- Concentrated where data/terrain rules indicate, especially relevant southern/southeastern zones.
- Dune orientation influenced by prevailing wind configuration and constrained by roads/coast.
- Multi-scale shape: base DEM, broad dune form, ripple normal/detail.
- No sharp fantasy mountains.
- Loose-sand physical material, wheel sinkage/rolling resistance, dust, tire tracks.
- Windward/leeward shading and sand accumulation near barriers.
- Distinct wet/compacted sand near shore.

C. Sabkha/salt flats

- Very flat, pale/gray-white crust, polygonal/cracked detail, occasional darker damp patches.
- Strong sun reflection but high roughness variation.
- Soft/damp traction zones where appropriate.
- Avoid placing ordinary vegetation/buildings without mapped evidence.
- Seasonal/rare wetness configuration must be data-driven and bounded.

D. Rawda/depressions and vegetated pockets

- Slightly lower terrain where runoff/soil permits more vegetation.
- Greener after rare rain according to seasonal profile.
- Farms/compounds only from mapped data or documented regional procedural selection.
- Do not create permanent streams without evidence.

E. Coastal mudflat/tidal flat

- Gentle elevation/depth transition.
- Wet mud/sand roughness and waterline darkening.
- Tide-dependent exposed area if data resolution supports it.
- Boat grounding and pedestrian sinking/slowing only in designated material zones.
- Wading birds optional through wildlife LOD.

F. Mangroves

- Especially important around Al Thakhira and other mapped mangrove zones.
- Distinct mangrove roots/canopy clusters, shallow channels, mudflat transition.
- GPU instancing/impostors.
- Collision only near player/boat.
- Protected/no-damage gameplay treatment; no missions encouraging destruction.

G. Urban/industrial/reclaimed land

- Engineered flat pads, drainage, roads, walls, lots, warehouses, skyline, cranes, tanks, port surfaces, and construction zones based on epoch.
- Public exterior/generalized industrial massing only.
- Reclaimed/artificial coastline must match the world epoch.
- No fictional chemical hazards or sensitive operational labels.

H. Agricultural/farm areas

- Mapped farms/greenhouses/compounds, irrigation geometry only from legal public data or generic non-operational visuals.
- Date palm/windbreak rows where supported.
- Restricted/private boundaries respected.

Terrain blending:

- Use splat/material weights generated by classification and slope/elevation/coast distance.
- Normalize weights.
- Avoid repeating visible texture grids.
- Use macro color variation, detail normals, stochastic/rotated samples where affordable.
- Roads/building pads override terrain safely without z-fighting.
- Terrain normals derive consistently from final height field.
- Collision height matches rendered terrain within documented tolerance.

Microdetail/performance:

- Near stones/shrubs/debris are instanced and pooled.
- Far terrain bakes macro detail.
- Tire/foot tracks use decals/virtual texture-like clipmaps with strict lifetime/budget.
- ECO shortens microdetail/track distance.


9. COAST, GULF WATER, TIDES, AND MARINE WORLD
---------------------------------------------

Water classes:

- Open Gulf water.

16. SHARED SIMULATION, UNITS, COLLISION, AND FIXED TIMESTEP
----------------------------------------------------------

Use explicit conventions everywhere. Do not let individual vehicle modules invent incompatible units or axes.

Units:

- Distance: metres.
- Mass: kilograms.
- Time: seconds.
- Linear speed: metres/second internally.
- Angular speed: radians/second internally.
- Force: newtons.
- Torque: newton-metres.
- Pressure: pascals when needed.
- Temperature: degrees Celsius for configuration/UI and kelvin where a formula requires absolute temperature.
- Vehicle HUD: km/h by default; optional knots for boat/aircraft.
- Gravity magnitude: configurable near 9.80665 m/s², applied consistently.
- Salt-water density: named regional configuration near a physically plausible value, never a scattered magic number.
- Air density: supplied by the weather/atmosphere model and clamped to a physically plausible game range.

Coordinate convention:

- Document one right-handed world convention, preferably X east, Y up, Z north (or another engine-native convention used consistently).
- Document positive yaw/pitch/roll and quaternion multiplication order.
- Convert GIS axes exactly once in WorldTransform.
- Render, physics, audio, AI, and save systems use the same transform contract.
- Unit tests verify cardinal directions, runway headings, vehicle forward vectors, and Arabic/English compass labels.

Fixed simulation:

- Bullet and all force models run at a fixed 60 Hz physics step:

      fixedDt = 1.0 / 60.0

- Rendering remains independently capped at 30/20/15 FPS.
- Use a bounded accumulator:

      frameDt = clamp(monotonicNow - previousNow, 0, 0.10)
      accumulator += frameDt
      substeps = 0
      while accumulator >= fixedDt and substeps < 4:
          sample buffered controls for this simulation time
          update deterministic weather forces needed by physics
          update pure force models
          apply forces and torques to Bullet bodies
          step Bullet exactly fixedDt
          synchronize contacts, wheels, seats, damage, and gameplay state
          accumulator -= fixedDt
          substeps += 1
      interpolationAlpha = accumulator / fixedDt
      render interpolated previous/current transforms

- If the accumulator exceeds the substep cap, discard or gradually recover excess according to a documented anti-spiral policy; never run hundreds of catch-up steps after pause.
- Reset timing safely after pause/resume/loading/debugger stalls.
- Buffer touch/gamepad input so short button presses are not lost between render and physics ticks.
- Apply one-shot actions exactly once.
- Camera and visual interpolation never feed a fake transform back into physics.

Simulation ordering per fixed tick:

1. Resolve queued origin rebase before stepping.
2. Activate/deactivate safe streamed collision bodies.
3. Read control snapshot.
4. Update environment samples: wind, air density, water height/current, surface material.
5. Human/vehicle force calculation.
6. Apply external forces/torques.
7. Bullet step/contact solve.
8. Read contacts/suspension/wheels/landing gear.
9. Update damage, seats, interactions, AI safety, and last-safe state.
10. Store current transform for render interpolation.
11. Dispatch bounded audio/particle events without allocating in hot loops.

Collision layers/masks:

- TERRAIN.
- STATIC_BUILDING.
- ROAD_BARRIER.
- HUMAN.
- PLAYER_CAR.
- TRAFFIC_VEHICLE.
- BOAT.
- HELICOPTER.
- AEROPLANE.
- TRANSIT.
- WILDLIFE.
- DYNAMIC_PROP.
- WATER_TRIGGER.
- INTERACTION_TRIGGER.
- RESTRICTED_ZONE_TRIGGER.
- PARTICLE/VISUAL_ONLY where no physics collision is required.

Define a collision matrix in one tested configuration file. Triggers must not create solid contact impulses. Never rely on undocumented default masks.

Collision geometry rules:

- Static terrain/buildings may use optimized static triangle/heightfield shapes.
- Dynamic objects use convex hulls, primitives, or compound convex shapes.
- Never use a concave dynamic triangle mesh for a moving vehicle.
- Render mesh and collider are separate assets with bounds validation.
- Fast car/aircraft bodies use continuous collision detection or explicit swept safety checks.
- Runways/roads/bridge decks have continuous collision with no tiny seam gaps.
- Coast/water triggers overlap terrain predictably without double solid surfaces.
- Collision chunks activate before visible focus can reach them and deactivate only outside a hysteresis safety ring.

Physics materials:

- Central registry maps compiled terrain/road/water/structure material IDs to friction, restitution, rolling resistance, human traction, tire model coefficients, dust/spray effects, footstep audio, and track/decal type.
- Separate Bullet contact friction from higher-level tire/hydrodynamic models; avoid multiplying incompatible friction twice.
- Restitution remains low for ordinary terrain/vehicles unless a specific material requires bounce.
- Material lookups are allocation-free.
- Unknown material uses a safe conservative fallback and logs once.

Solver/body policy:

- Configure Bullet solver iterations and contact thresholds through named quality-tested settings.
- Sleeping enabled for unoccupied/inactive dynamic objects.
- The occupied vehicle and immediate safety objects remain active.
- Distant traffic/transit uses route/proxy simulation, not thousands of awake rigid bodies.
- No direct transform changes on a dynamic body during normal operation.
- Teleport only for explicit spawn/recovery/origin-rebase operations; clear/update broadphase and interpolation state correctly.
- Constraints, compound child offsets, center of mass, and inertia must be finite and validated.
- Clamp only pathological forces; do not hide an unstable model with arbitrary velocity caps.

Determinism expectations:

- Pure force/configuration tests must be deterministic for the same inputs.
- Chunk generation/selection must be deterministic.
- Bullet does not need bit-identical cross-device output, but scenarios must remain within numeric tolerances.
- Random gameplay/environment events use explicit seeded streams separated by subsystem so a visual particle change does not alter vehicle physics.

Configuration validation at startup/build:

- Positive finite mass/inertia dimensions.
- Center of mass inside a documented plausible envelope.
- Nonzero wheel/rotor/wing/hull dimensions.
- Force coefficients finite and bounded.
- Suspension rest/travel valid.
- Collider scale matches render scale and SI metres.
- No NaN/infinity in spawn transforms or configuration.
- Control axes/dead zones/rates valid.

Shared simulation tests:

- Same 10-second force scenario rendered through 15, 20, 30, 60, and irregular FPS sequences produces close final physics state.
- Pause/resume causes no giant impulse.
- Origin rebase preserves active constraints and velocities.
- Sleeping body wakes on valid contact.
- CCD catches representative maximum-speed barrier impact.
- Material registry returns expected road/sand/sabkha/water behavior.
- Trigger overlaps do not create solid impulses.
- No hot-loop allocation in a profiled fixed-step sequence.

19. BOAT/DHOW-INSPIRED PHYSICS FOR SHALLOW GULF WATER
-----------------------------------------------------

Create an original unbranded small workboat, fishing boat, center-console craft, or dhow-inspired powered vessel.

Hull:

- Rigid body with 8–16 distributed buoyancy sample points appropriate to hull.
- Visual hull and simple convex/compound collision.
- Designed waterline/mass/center of mass.

Per buoyancy point:

- Sample analytic water height/normal/velocity.
- Compute submersion/displaced volume proxy.
- Apply upward force at point:

      buoyancy = waterDensity * displacedVolume * gravity

- Apply vertical damping based on relative hull/water velocity.
- Clamp force to prevent numerical spikes.

Hydrodynamics:

- Forward drag.
- Stronger lateral resistance.
- Vertical damping.
- Angular damping based on submersion.
- Propeller thrust based on throttle/RPM/submersion/advance speed.
- Rudder/vectored-thrust steering from water flow.
- Bounded planing lift at speed.
- Wind drag above waterline.
- Tide/current advection.
- Shallow-water resistance.
- Grounding/beaching/mudflat behavior.
- Propeller thrust reduction out of water/too shallow.

Gulf-specific:

- Calm protected marina water versus open-water chop.
- Shallow turquoise bank behavior.
- Mudflat/mangrove channels.
- Khor Al Adaid water/desert shoreline.
- Heat/haze visual, not a fake force.
- Channels/port barriers from public map data.

Visual/audio:

- Wake from speed/hull load.
- Bow spray/prop wash/foam pooled.
- Engine pitch/load.
- Hull slap/creak/water.
- Generic navigation lights.
- Optional sail is outside minimum unless physically implemented.

Boat acceptance:

- Floats at intended waterline.
- Recovers from moderate roll/pitch.
- Energy decays without throttle/waves.
- Turns mainly with flow/speed unless vectored thrust.
- Tide/current drift bounded.
- Wave render and physics synchronized.
- Beaches without falling through/climbing cliffs.
- Shallow channels prevent unrealistic deep-draft travel.
- Origin rebase preserves wave/boat state.


20. HELICOPTER PHYSICS FOR HOT, DUSTY, WINDY CONDITIONS
-------------------------------------------------------

Create an original fictional light utility helicopter.

Required properties:

- Fuselage mass, center of mass, inertia, drag areas.
- Main rotor radius/area/position/inertia/RPM.
- Tail rotor/anti-torque position/authority.
- Skids/contact compliance.
- Engine/rotor spool state.

Forces:

      thrustMagnitude = Ct * airDensity * rotorArea * tipSpeed^2 * collective
      thrustDirection = normalized(rotorUp + cyclicPitchTerm + cyclicRollTerm)
      mainRotorForce  = thrustDirection * thrustMagnitude

Include:

- Collective thrust.
- Cyclic tilt and pitch/roll moments.
- Main-rotor reaction torque.
- Tail rotor/yaw.
- Translational lift.
- Ground effect based on height and surface extent.
- Parasite drag.
- Simplified bounded vortex-ring/settling-with-power behavior.
- Engine loss and simplified autorotation/rotor decay.
- Wind/gust response.
- High ambient temperature/air-density configuration affecting available lift modestly and physically consistently.
- Optional stability assist through bounded torques, not position lock.

Dust/brownout:

- Trigger on rotor wash over loose sand/dust near ground.
- Pooled particles with depth/visibility profile.
- Dust amount from surface material, collective, rotor height, wind.
- Never make a full-screen opaque effect in LOW/ECO.

Landing:

- Gentle landing settles.
- Side slope limits.
- Hard landing damages/skids/vehicle state.
- Rotor danger/collision zone.

Acceptance:

21. AEROPLANE PHYSICS, RUNWAYS, AND DENSITY ALTITUDE
----------------------------------------------------

Create an original fictional light single-engine propeller aeroplane.

Use a verified public civilian/gameplay airfield spawn. HIA/Doha airport public surfaces may be represented; military/restricted airfields must not be player bases. Use fictional aviation/livery/operations and never reproduce real airline operational systems.

Aircraft data:

- Mass/center of mass/inertia.
- Wing area/span/chord/aspect ratio.
- Aerodynamic center.
- Horizontal/vertical stabilizer geometry.
- Propeller/engine parameters.
- Landing gear positions/suspension/wheels/brakes/steering.
- Control-surface limits/rates.

Air state:

- Local air velocity = body point velocity minus wind.
- Air density from a bounded standard-atmosphere approximation modified by configured temperature/pressure; document that it is a game model.
- High heat increases density altitude and reduces lift/propeller/engine performance consistently.

Dynamic pressure:

      q = 0.5 * airDensity * airspeed^2

Lift:

      lift = q * wingArea * Cl(angleOfAttack, flapSetting)

Drag:

      drag = q * wingArea * (Cd0 + inducedDragFactor * Cl^2)

Cl behavior:

- Approximately linear in normal range.
- Peaks near stall angle.
- Declines post-stall.
- Control authority declines at low speed/stall.
- No unlimited lift at extreme alpha.

Required systems:

- Wing/tail/vertical stabilizer contributions.
- Elevator/aileron/rudder.
- Flaps and trim.
- Propeller thrust versus RPM/throttle/airspeed/density.
- Engine response/spool.
- Ground effect.
- Crosswind/gust.
- Landing-gear spring/damper.
- Rolling friction/brakes/nose or tail steering.
- Hard-landing/overspeed/excess-G damage thresholds.
- CCD/swept collision.

Runways/airports:

- Actual projected length/heading/width from legal open data.
- Public exterior runway/taxiway/apron/terminal massing.
- Correct terrain pad/markings/lights at game fidelity.
- No hidden runway scaling.
- No secret/security interiors.
- Preload approach/departure terrain and skyline.

Acceptance:

- Physical ground roll.
- Takeoff only with sufficient airspeed/lift.
- Hot-day density effect measured but not exaggerated.
- Stall/recovery.
- Correct controls.
- Flaps alter lift/drag.
- Crosswind approach.
- Gear compression/braking.
- Engine-off glide.
- Full peninsula circuit with streaming/origin stability.
- No terrain holes at altitude or approach.

27. THERMAL, BATTERY, AND PERFORMANCE REQUIREMENTS
--------------------------------------------------

Phone heat is a release blocker.

Frame pacing:

- No unrestricted default 60/90/120 FPS loop.
- Balanced default: approximately 30 FPS.
- Battery saver/moderate thermal: approximately 20 FPS ECO.
- Severe thermal: approximately 15 FPS.
- Rendering, physics scheduling, audio, AI, and streaming pause correctly with Activity/screen lifecycle.
- Respect screen timeout; do not force unattended GPU use.
- Thermal service polled infrequently or listener-based.

ECO reduces work:

- Dynamic resolution down.
- Dynamic shadow sampling disabled/simplified.
- Shorter high-detail/vegetation/prop/light/particle ranges.
- More aggressive building/vehicle LOD.
- Reduced traffic/pedestrian/transit/wildlife counts/update rates.
- Reduced water reflection/rain/dust/night-window updates.
- Preserve occupied-vehicle physics/control and collision safety.

Suggested balanced budgets (measure and adapt):

- 33.3 ms at 30 FPS.
- Main game/simulation ideally below 6–8 ms average.
- Draw calls preferably below 150–250.
- Visible triangles roughly 200k–500k depending on device/profile.
- Nearby fully simulated dynamic bodies below approximately 100–150.
- One main directional shadow system.
- Texture residency approximately 256–384 MB balanced; lower in LOW/ECO.
- Bounded Java/native/Bullet/audio/decode memory.
- No major per-frame allocations/GC spikes.

Optimization:

- Hierarchical country/chunk culling.
- Frustum/distance/altitude culling.
- Static batching by chunk/material.
- Mesh/collision/animation LOD.
- Texture atlases/mipmaps/compression/shared pages.
- Instancing/impostors.
- Object pools.
- Sleeping/proxy distant physics.
- Predictive streaming.
- Bounded decode/upload.
- Far shader simplification/fog cutoff.
- Development overlay: FPS, CPU/GPU frame, draw calls, triangles, chunks by state, queue, RAM/native/texture/mesh bytes, bodies, agents, origin, thermal.

Profiles:

LOW
- Aggressive LOD/ranges, low particles/traffic, 512/no shadows based capability.

BALANCED
- Default 30 FPS, compact throttled shadow, normal materials/ranges.

HIGH
- Improved LOD/shadow/reflection/lights, still thermally protected.

ECO
- Automatic battery/thermal override displayed in HUD and not bypassable under severe pressure.

APK size permission never overrides thermal/memory requirements.

NOTES FOR THE PERSON USING THIS PROMPT
--------------------------------------

1. “Entire country” means all legally recognized Qatari land represented by the chosen consistent authoritative/open boundary dataset, every municipality, all peninsula regions, and all included islands. Surrounding water/airspace is added for gameplay and is not a political maritime-boundary claim.
2. Qatar should remain 1:1 scale. Its real road distances, runways, coastline, and desert make car/boat/helicopter/aeroplane gameplay meaningful. Streaming and a floating origin solve scale; global compression would make the country feel unreal.
3. Qatar is not uniformly covered in tall dunes. A convincing environment requires rocky limestone/gravel plains, sand regions, sabkha, rawda/farms, mangroves, tidal flats, urban/reclaimed land, industrial massing, beaches, and shallow Gulf water in correct data-driven locations.
4. App size may be large, but runtime RAM/GPU/thermal limits remain strict. GitHub Actions artifacts or Releases should host an APK too large for a normal Git push.
5. Qatar changes rapidly. Keep a world epoch and do not mix old/new roads, coastline, stadiums, construction, and transit without disclosure.
6. Public map-level airport/port/industrial/military geometry may be generalized, but never add restricted interiors, credentials, security procedures, hidden infrastructure, or operational detail.
7. Correct Arabic requires shaping, BiDi, RTL, and a licensed font. Reversing strings or rendering disconnected letters is not acceptable.
8. A CI emulator is not a physical phone. Test long Doha driving, full-country flight, memory, battery, Android thermal status, Arabic rendering, and controls on intended devices before claiming final performance.
9. Keep all data and asset licenses so the APK can be redistributed legally.
